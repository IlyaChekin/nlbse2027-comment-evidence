# NLBSE 2027 · почему MAT пропускает комментарии

На двух отложенных группах сохранили **0 FP в каждом проекте**. Новые признаки вернули **0 из 77** пропусков на A и **0 из 23** на B. Сравнение опирается на 38 997 функций, разбиение сделано до обучения и совпадает с предыдущим раундом MAT. Группа A включает Chromium, QEMU и FFmpeg, группа B включает Firefox, Android, PHP, ImageMagick, radare2, krb5 и file. [Проверка базовых решений](mat/margins.json)

| Метод | Восстановлено на A при 0 FP | Восстановлено на B при 0 FP |
|---|---:|---:|
| Точное сопоставление тела функции после нормализации имён и сопоставление комментариев без маркера | 0 / 77 | 0 / 23 |
| Разреженный классификатор с удалением тегов в любом месте или только перед функцией | 0 / 77 | 0 / 23 |
| Попарное обучение на реальных пропусках с тегом перед функцией | 0 / 77 | 0 / 23 |

Точное сопоставление не нашло ни одного подходящего обучающего совпадения в этих 100 пропусках. Для разреженного контроля удаление дало 1 879 синтетических примеров при любом расположении тега и один при положении строго перед функцией. Дефицит второго типа виден уже в fit. ## Подтверждение причины и проверка новой головы

Сверили все **302** пропуска fit с закреплённым снимком Linux. Код сопоставляли по полной последовательности токенов, сохраняя строковые литералы. У **241** функции нашли тег в соседнем предшествующем комментарии, у **4** тег внутри исходного диапазона. У 17 однозначных совпадений в этих местах тега не было, ещё 40 функций однозначно сопоставить не удалось. Из 1 604 отрицательных контролей похожей длины в тех же файлах однозначно сопоставили 1 393. Ни у одного из сопоставленных контролей тега в этих местах не было. Эти числа относятся к выбранным файлам Linux. [Исходные хеши и построчная сверка](mat/fit_provenance.json)

Обучили попарный линейный ранжировщик на **230** пропусках с подтверждённым тегом перед функцией и **1 215** отрицательных контролях, всего **1 332 пары**. Сравнили с 250 однозначно сопоставленными пропусками любого происхождения и с обучением на естественных пропусках без пар. Признаки для теста вычисляются из конкурсного поля `Function`. Исходные снимки используются для формирования обучающих пар. [Протокол, веса и пороги](mat/paired_provenance/policy.json)

Попарный ранжировщик отдельно дошёл до первого пропуска ценой **1 FP** у QEMU и у krb5. Это диагностические пороги, рассчитанные по меткам конкретного проекта. Порог, замороженный на разработке, вернул 0 пропусков и добавил 3 FP на A, на B все решения совпали с базой. Все 48 комбинаций модели и калибровочного лимита 0, 1, 2, 4, 8, 16 дополнительных FP проверены по F1. Максимум F1 на разработке достигался при исходных решениях MAT. [Построчные результаты](mat/paired_provenance/results.json) · [Цена первого возврата](mat/margins.json) · [Калибровка с мягким бюджетом](mat/frontier.csv)

## Дополнительная проверка vulnerability

Сравнили дистилляцию в дополнительную голову компактной модели, дообучение двух последних блоков и дообучение с весом по пользе сильного учителя на внефайловых прогнозах. При сохранённых обучающих целях от UniXcoder и регуляризации исходных выходов воспроизвели весь прежний маршрут, включая условные вызовы сканера и поправки обоих исходов. Контроль с замороженным энкодером дал побитовое совпадение основных оценок. Два варианта с дообучением последних блоков изменили 111 и 138 маршрутов сканера на A и 16 и 20 на B. [Конфиги и веса](trained/) · [Оценки](continuation_comparison.csv)

Вариант с выборочной дистилляцией и поправкой в полосе 0,4 дал +11 TP на A и +3 TP на B при прежнем FP каждого проекта. Повторная настройка порога контрольного ранга на самих проектах дала +1 и +4 TP, поэтому чистый прирост ранжирования составил +10 и −1 TP. На официальной внутренней калибровке результат 0 TP и 0 FP, на независимой внутренней части −2 TP и −2 FP с небольшим снижением F1. Ни одна из 54 комбинаций не прошла отбор по обеим проектным группам, калибровке и независимой внутренней части. [Сводка](summary.json)

## Цель 0,97

Лучший проверенный публичный результат **0,9639998** получен на 30 655 функциях. У MAT 444 TP, 0 FP и 61 пропуск. При прежней стоимости и vulnerability для достижения 0,97 нужны **19 дополнительных TP MAT без новых FP**. У **41 из 61** публичного пропуска уже подтверждён отсутствующий во входе тег. У оставшихся 20 происхождение пока не установлено. Даже при нулевых затратах текущие бинарные решения дают 0,966174. При фиксированных MAT и стоимости альтернативные расчётные цели составляют 390 дополнительных TP vulnerability или устранение 413 FP vulnerability. [Расчёт по подписанным прогнозам](summary.json) · [Сверка публичного контекста](../round26/README.md) · [Архив раунда 29](../submission/NLBSE2027_round29_recall_tool.zip)

Повторный прогон воспроизвёл **61 310** публичных решений. Из 460 FP vulnerability **274** пришлись на положительный ответ сканера, **96** на отрицательный и **90** на функции без запроса. Среди 512 пропусков **364** получили точный отрицательный ответ и **132** остались без запроса. Публичный срез описывает размер когорт для следующей проверки. ## Воспроизведение

Команды из корня экспериментов на Banana используют тот же датасет, разбиение и модели. Повторная загрузка исходников для fit нужна только для проверки происхождения и уже сохранена в `fit_provenance.json`. Хеши данных, provenance, весов и прогнозов сверяет `summarize.py`.

```bash
export OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2
py=.venv/bin/python
round=nlbse/round31
mat=$round/mat
$py "$mat/transfer.py"
$py "$mat/placement.py"
$py "$mat/audit_fit.py"
$py "$mat/paired_provenance.py" "$mat/fit_provenance.json"
$py "$mat/margins.py"
$py "$mat/frontier.py"
for part in test_a test_b official; do
  $py nlbse/cuda_launch.py "$round/continue_fit.py" "$part"
  $py nlbse/cuda_launch.py "$round/continue_eval.py" "$part"
done
$py nlbse/cuda_launch.py "$round/audit29.py"
python3 "$round/summarize.py"
```
